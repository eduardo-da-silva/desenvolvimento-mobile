02

O que NÃO fazer

axios dentro de arquivo .vue

02 · anti-padrão

Funciona... e é um problema

① URL espalhada

Trocar de servidor = caçar em todos os componentes.

② Sem estado compartilhado

Outra tela precisa das tarefas? Faz outra requisição.

③ Erro e loading repetidos

Cada componente reinventa o try/catch.

02 · anti-padrão

O custo real

④ Difícil de testar

Para testar a tela é preciso simular a rede dentro do componente.

⑤ Impossível mudar de ambiente

localhost:8001 vai para produção junto com o build.

⑥ No PWA, ainda pior

A URL do cache do Workbox e a do código precisam coincidir. Duas fontes de verdade.

Teste mental

"O servidor mudou de localhost:8001 para api.escola.dev. Quantos arquivos eu edito?"

Camada de serviço + plugin

Um lugar para o cliente HTTP, outro para os endpoints

03 · serviço

Cliente HTTP e serviço de tarefas

Uma única instância criada aqui. A baseURL não aparece: quem define é o plugin.

03 · plugin

Plugin: onde a URL base é decidida

Como funciona

app.use(plugin, opts) chama install(app, opts) uma vez, antes do mount.

Vantagem

Config de ambiente, interceptors e (depois) o token JWT ficam em um arquivo.

Reuso

Em teste: app.use(apiPlugin, { baseURL: mock }).

03 · plugin

main.js: trocando a URL em um lugar só

O Vite substitui import.meta.env.* no build. Só variáveis com prefixo VITE_ chegam ao navegador.

03 · plugin

Mais flexível: URL em tempo de execução

Para quê?

Apresentação em sala: cada aluno aponta para o http://IP-do-professor:8001 sem rebuild.

No celular

localhost é o próprio aparelho! Use o IP do PC (ou o domínio) no lugar.

E com PWA/APK: a URL do runtimeCaching do Workbox deve cobrir o mesmo host que o plugin usa.

Duas formas de usar a camada de serviço

opção A

View → Store → Serviço

TaskListView
↓
useTasksStore
↓

Estado compartilhado entre telas, cache em memória, loading/erro centralizados.

opção B

View → Serviço

TaskSummaryView
↓
tasksApi

Estado local e descartável: resumo, busca, relatório, formulário avulso.

Nos dois casos o componente continua sem axios e sem URL.

04 · chamadas

Opção A: a store chama o serviço

Só a store conhece o serviço

As views chamam store.fetchTasks(); a store chama tasksApi.

Estado único

Lista, loading e erro valem para todas as telas.

04 · chamadas

Opção B: a view chama o serviço

Bom quando

O dado vive e morre com a tela. Não há motivo para guardá-lo na store.

Cuidado

Se duas telas precisarem do mesmo dado, promova para uma store.

04 · chamadas

Qual escolher?

A · Store → ServiçoB · View → Serviço

Na dúvida, comece em B e suba para A quando surgir o segundo consumidor.

resumo

O que levar daqui

  • Leia o Swagger antes de codar: é o contrato.
  • Nunca axios nem URL em .vue.
  • src/api/http.js cria o cliente, tasksApi.js mapeia endpoints.
  • O plugin define baseURL e interceptors no main.js.
  • Estado compartilhado → store; local → serviço direto.
  • ESLint trava a regra automaticamente.
